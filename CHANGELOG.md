# CHANGELOG
## Unreleased
* New features:
    - Ubuntu 26.04 is listed in the supported operating systems (`metadata.json`), so the specs run for it
    - the keyfiles and the `NetworkManager.conf` are managed by the new `networkmanager_keyfile` type, its `ruby` provider renders the GLib key file from the hash of sections when the catalog is applied (it replaces `templates/ini.epp` and `networkmanager::ini_value`); the diffs of the changes are shown (when the `show_diff` setting of Puppet is on) with the values of the secrets (passwords, `psk`, wep keys, private keys, `vpn-secrets`, ...) censored, `$networkmanager::show_diff` (`true` by default) switches them off, `$networkmanager::secret_keys` adds more censored settings; `puppet resource networkmanager_keyfile` shows only the checksums of the content
    - the `disabled` IPv6 method is changed to `ignore` (with a warning) by the provider when the installed NetworkManager does not support it (< 1.20), it reads `nmcli --version` (a read only question, it was an `nmcli connection add` with an invalid value) when the catalog is applied, so it works when NetworkManager is installed by the same run; when the version can not be read the resource fails instead of guessing that the method is supported
    - the link of every `networkmanager::ifc::*` define (bond, bridge, vlan and the slaves too, not only `::connection`) with `$state => 'down'` is handled by the new `networkmanager_link` type, its `nmcli` provider decides when the catalog is applied: NetworkManager supporting it (1.57+, backported to RHEL 9.9 / 10.3) gets `nmcli device set <ifc> managed --permanent down`, so the device is unmanaged and down persistently, the others `ip link set <ifc> down`; switching back to `'up'` runs `nmcli device set <ifc> managed --permanent yes` when the device is unmanaged
    - `$networkmanager::connections_dir` (`/etc/NetworkManager/system-connections` by default) sets the directory of the connection keyfiles
    - the `networkmanager` class has the `ignore_unsupported_os` parameter (`false` by default): the module still fails on an operating system family it has no package name for, `true` skips the package installation with a warning
    - the new parameter `networkmanager::uuid_seed`: the UUIDs of the connections are derived from it, the certname of the node by default (as before), so they can be kept when a node gets another certname
    - `networkmanager::ifc::vlan` has the IP parameters of `networkmanager::ifc::connection` (`ipv4_method`, `ipv4_address`, `ipv4_gateway`, `ipv4_dns`, `ipv4_may_fail`, `ipv6_method`, `ipv6_address`, `ipv6_gateway`, `ipv6_dns`, `ipv6_dhcp_duid`, `ipv6_addr_gen_mode`, `ipv6_privacy`, `ipv6_may_fail`); the methods are `auto` (`disabled`/`ignore` for a vlan that is a port, `master`), the vlan writes the `[ipv4]` and `[ipv6]` sections now, with the server defaults (`ipv6_addr_gen_mode` and `ipv6_privacy` 0). The vlan has the `mac_address` for the DHCP DUID (the MAC address of its parent; not written to the keyfile), so a vlan with the IPv6 method `auto` or `dhcp` fails to compile without it, as the bond and the bridge do, unless the DUID is `unset` or given
    - the new parameter `slave_type` of `networkmanager::ifc::connection`, `::bond` and `::bridge` (the type of the master, see the breaking changes), the `slave_type` of `networkmanager::ifc::vlan` is checked by the new `Networkmanager::Port_type` type
    - new `networkmanager::normalize_mac` function, the MAC addresses are written as `aa:bb:cc:dd:ee:ff`, see the behaviour changes
* Breaking changes (the code which uses the module has to be changed):
    - **BREAKING:** the `master` of `networkmanager::ifc::connection`, `::bond` and `::bridge` needs the new parameter `slave_type` (`Networkmanager::Port_type`: `bond`, `bridge`, `team`, `ovs-bridge`, `ovs-port`, `vrf`), the compilation fails without it. NetworkManager refuses a keyfile with a master and without the port type (`connection.port-type: Cannot set 'controller' without 'port-type'`), so the old code produced a keyfile which could not be used. The `slave_type` of `networkmanager::ifc::vlan` is a `Networkmanager::Port_type` too (the default is still `'bridge'`). Without a `master` the `slave_type` is ignored. Example of the change:

      ```puppet
      # before: compiled, but NetworkManager refused the connection
      networkmanager::ifc::bond { 'bond0': ipv6_method => 'ignore', master => 'br0' }

      # now: fails to compile without the slave_type
      networkmanager::ifc::bond { 'bond0': ipv6_method => 'ignore', master => 'br0', slave_type => 'bridge' }
      ```
    - the services are `Service['NetworkManager']` and `Service['NetworkManager-wait-online']` (the `.service` suffix is gone, the names work with systemd and OpenRC), fix the relationships in your code
    - the keyfiles are no more `file` resources (`File['/etc/NetworkManager/NetworkManager.conf']` and `File['.../<id>.nmconnection']` are `Networkmanager_keyfile[...]` now), fix the relationships in your code; the exec `shutdown link of connection <uuid>` is replaced by `networkmanager_link`
    - the `networkmanager` fact, `networkmanager::ipv6_disable_version` and `networkmanager::notify_ipv6_disabled` were removed (the fact had only the `version`, which was used just for the IPv6 `disabled` method; if you use `$facts['networkmanager']` in your code, use `nmcli --version` in your own fact)
    - `networkmanager::connection_keyfile_manage` and the classes `networkmanager::os`, `install`, `config`, `service` and `reload` are private (`assert_private()`), they can not be declared outside of the module; a relationship to them (eg. `Class['networkmanager::service']`) still works
    - `$networkmanager::config::no_auto_default` is a `Boolean`, the string branch which was never reachable is removed
* Behaviour changes to check when upgrading:
    - the connection `id` is validated by the new `Networkmanager::Connection_id` type (it is the name of the keyfile): printable ASCII (the space is allowed) without `/` and `\`, not starting with a dot; `networkmanager::ifc::bond` had no check of the `id` at all, it has the length check now too
    - the `interface_name` is validated by the new `Networkmanager::Interface_name` type (also for the title of an ethernet connection used as the interface name, and in `networkmanager_link`): 1 to 15 printable ASCII characters without `/`, `\`, `:`, `*`, `?`, `[`, `]` and whitespace, starting with a letter or a digit, not `all` or `default`; the old minimum of 3 characters is gone
    - the `unmanaged_devices` are validated by the new `Networkmanager::Unmanaged_device` type (a MAC address or an interface name, the globs like `docker*` are allowed, `;` is not) and the `plugins` by the new `Networkmanager::Plugin` type (lowercase names like `keyfile`, `ifcfg-rh`)
    - the UUID patterns of `networkmanager::activate_connection`, `reload_connection` and `connection_uuid` and the `$duid_prefix` use `\A...\z` instead of the line anchors `^...$`, so a multi-line value is not taken as an UUID (it was interpolated to the commands run as root)
    - the names of the sections and the settings of a `networkmanager_keyfile` are validated (no `[`, `]`, `=`, new lines), the values were escaped already; a name of a setting can not be empty or start with `#`, `[` or a white space either (GLib reads such a line as a comment or a section, the setting was lost silently), the names of the sections still can hold `=`, `/` and `+` (the sections of the WireGuard peers are named by the base64 public key)
    - the settings with `cookie`, `credential`, `api-key` and `auth-key` in the name are censored in the diffs too
    - the activation execs are virtual (`@exec`), not exported (`@@exec`), and `networkmanager::reload` collects them with `Exec <| tag == ... |>`: nothing else can inject an exec with the tag of the node through the exported resources, the commands and their order are the same, and the exported resources backend (`storeconfigs`, PuppetDB) is no more required
    - `erase_unmanaged_keyfiles` removes only the unmanaged `*.nmconnection` files (the only ones NetworkManager reads), other files of `connections_dir` are left alone; the managed keyfiles are recognized also when the `connections_dir` has a trailing slash (they were removed and rewritten in every run before)
    - `use_internal_resolv_conf => false` replaces the `/etc/resolv.conf` link by a copy of the file it points to (it created an empty file before, so the node had no DNS until NetworkManager rewrote it)
    - `erase_unmanaged_keyfiles` (`false` by default, so nothing is removed) is done by the new `networkmanager_keyfile_dir` type, the `system-connections` directory is not recursed any more
    - the packages notify `Service['NetworkManager']`, a new version of the package restarts the daemon
    - `wait_online => false` stops and disables `Service['NetworkManager-wait-online']` only on systemd hosts (`$facts['service_provider']` of stdlib is `systemd`), other service managers (OpenRC) have no such unit and the service is not managed there
    - the DHCP DUID (`ipv6.dhcp-duid`) is written for the connections in the state `down` too (it was dropped for them, so a profile activated outside of Puppet got another DUID and lease, and the keyfile was rewritten when the state changed)
    - `ensure => absent` of a connection with an `interface_name` or a `mac_address` sets the `networkmanager_link` to `managed` (the device unmanaged by an earlier `state => 'down'` stayed unmanaged for good); the exec `forget connection` is not `refreshonly` any more, so an interrupted removal is finished by the next run
    - the `mode` of `networkmanager_keyfile` has to be a string (`'0600'`), the Integer `420` was taken as the octal digits `0420`; the values of the settings must be strings, numbers, booleans or arrays of them (a nested array was written as a broken value), not checked for `ensure => absent`
    - `networkmanager::ifc::bridge`: `bridge_forward_delay` is `Integer[0, 30]`, `networkmanager::ifc::vlan`: `vlan_flags` is `Integer[0, 15]` (the values NetworkManager accepts)
    - the MAC addresses of `unmanaged_devices` and of the DUID are written as `aa:bb:cc:dd:ee:ff` (lowercase, colons): the dash form of `Stdlib::MAC` made an invalid DUID (`00:03:00:01:aa-bb-cc-dd-ee-ff`) and an `unmanaged-devices` value NetworkManager did not read as a MAC; `networkmanager_link` accepts the dash form and 20 bytes (InfiniBand) too (new `networkmanager::normalize_mac`)
    - the unused `hiera.yaml` and `data/common.yaml` (empty module data) were removed
    - `networkmanager_keyfile_dir` compares the paths through the symlinks of the directories, a link in the directory is not the file it points to
    - `networkmanager_keyfile` fails with a clear message for a user or a group that does not exist
* Fixes (from the review of the module):
    - `networkmanager::ifc::fallback` declared two contradictory relationships with `Class['networkmanager']` (it only worked because the class contained nothing), it is ordered after the class like the other defines
    - `Class['networkmanager']` contains its subclasses now, so a relationship to it (or the ordering of the defines of the module) means after the package, the configuration and the service; the activation execs run after `Service['NetworkManager']`
    - `ensure => absent` of the connections (all the `networkmanager::ifc::*`) deactivates the connection before its keyfile is removed and reloads NetworkManager afterwards, it kept the connection active before
    - `state => 'down'` deactivates the active connection on every run (the exec was refreshonly, so it ran only when the keyfile changed); the `networkmanager_link` of `networkmanager::ifc::connection` is ordered after the deactivation, before the activation for `up` (the old `before` pointed to an empty class)
    - a connection is activated after its master or parent connection (`master` of the connection, bond, bridge and their slaves, `master` and `vlan_parent` of the vlan) when the master is managed by the module
    - `networkmanager::reload_connection` waits at most 60 seconds for the NetworkManager D-Bus service (it waited forever, until the timeout of the exec) and does not rely on `PATH` for `gdbus`
    - the `networkmanager_link` provider fails when `nmcli device set` or `ip link set` fail (it ignored the result and reported the change as done)
    - `networkmanager_keyfile` keeps the `mode` of the resource when the content changes (it was reset to 0600, then changed back by the mode property), `puppet resource networkmanager_keyfile` lists only the `*.nmconnection` files, the `secret_keys` are matched case insensitively and the MACsec pattern is `mka-cak` and `mka-ckn` only
    - `Networkmanager::IPV4_ADDRESSES` and `IPV6_ADDRESSES` accept one address with the trailing semicolon (`10.0.0.5/24;`), the prefix of the IPv6 string format is 0 to 128, and every address of the IPv6 string formats (addresses and DNS servers) is validated as an IPv6 address (`1.2.3.4/64` or `::::` were written to the keyfile)
    - the `mac_address` of `networkmanager::ifc::connection` and of the slaves is written into the section of the connection type (`ethernet`, `802-11-wireless` for `wifi`), it was always `[ethernet]`; other types fail with a hint to use the `additional_config`
    - the `additional_config` of the connections can not set `connection.uuid` (the connection is activated by the generated one); `networkmanager::ifc::fallback` activates the uuid from its `config`, which has to be an UUID
    - `networkmanager` fails with a clear message when neither the certname nor the fqdn is known (the UUIDs and the activation tag need it), `$facts['networking']['fqdn']` is looked up safely, `$version` can not be an empty string
    - a change of `NetworkManager.conf` restarts only `Service['NetworkManager']` (it restarted the wait-online service too), the `connections_dir` has the mode 0700
    - `networkmanager::ifc::fallback` accepts an `interface-name` which YAML gives as a number
    - `networkmanager_link` with `down` also shuts the link down with `ip` when `managed --permanent down` left it up (the resource reported the change in every run), with `managed` it brings up the link that `ip` shut down on a NetworkManager without the permanent unmanage (nothing brought it up when the activation of the connection failed); a device that does not exist is the state `missing`, in sync in both states
    - `UUID=<uuid>` as a `master`, `vlan_parent` or any other id is refused (the plain UUID is meant; it was hashed into an unknown UUID and failed at the activation)
    - the `additional_config` of the connections can not set `connection.id`, `interface-name`, `master` and `slave-type` either (the module sets them from its parameters and orders the activation by them), use the parameters
    - `networkmanager_link` finding the device by the MAC address fails when more than one device has it (it took the first one in the order of the directory) and survives an interface that vanishes during the lookup
    - `networkmanager_link` took a device that does not exist for an up link (the error message of `ip` was taken for its output), so `state => 'down'` failed the run on every run; the exit status is checked and a missing device is `down`, as the README says
    - a `master` or `vlan_parent` equal to the connection itself is refused at the compilation (it made a dependency cycle of two execs named by UUIDs); the ordering ignores such a reference in `networkmanager::ifc::fallback`
    - the `mac-address` of the connections is written normalized (`aa:bb:cc:dd:ee:ff`) like the other MAC addresses
    - `networkmanager::ifc::fallback` has the parameters `interface_name` and `mac_address` for the link of its device (not written to the keyfile), like the other defines; the other defines create the link for the removed connection too
    - `networkmanager` does not fail on a missing `os.family` fact with an unreadable error, it is an unsupported family (the warning with `ignore_unsupported_os`)
* Maintenance:
    - the private defined resource `networkmanager::connection_manage` is the common part of all the `networkmanager::ifc::*` defines (the check of the id, the keyfile, the activation, the link), the repeated code of the seven defines is gone; the relationships `Networkmanager::Ifc::<x>[$title] ~> Class['networkmanager::reload']` were no-ops (the class is empty) and are removed, `Class['networkmanager'] -> Networkmanager::Ifc::<x>[$title]` is still true
    - the Ruby code is linted by RuboCop (`.rubocop.yml`, the step `Ruby lint` of the CI, `rubocop` in the `Gemfile`, `json` is pinned below 3 because facterdb still calls `JSON.create_id=`), the files of `lib/`, the `Gemfile` have `# frozen_string_literal: true`
* Tests: the specs run with the oldest stdlib the metadata allows (5.2.0) too, `.fixtures.yml` pins stdlib `v9.7.0`, RuboCop is pinned to `~> 1.82`, an unknown operating system in the generated facts is an error (it was taken as RedHat); the specs of `networkmanager_link` (type and provider), of the lifecycle (`absent`, `down`, `up`) and the order of the activation of every kind of connection, of the detection of the `disabled` IPv6 method, of the facterdb facts of every operating system listed in `metadata.json` that facterdb knows, of the values NetworkManager refuses; the directed order of the subclasses, the self references, the values of the settings, the content of `networkmanager::ifc::fallback`, `plugins=` and the package of every family in the facterdb specs; the specs do not pin the order of the settings in the keyfile, `spec/default_facts.yml` (legacy facts the module never read) was removed, `compact_keyfile` is simpler
* Documentation: `REFERENCE.md` is generated by puppet-strings (`bundle exec puppet strings generate --format markdown --out REFERENCE.md`, checked by the CI), the comments of the functions are in the puppet-strings format (`@param`), it was updated by hand and had drifted from the code; the `additional_config` documents the empty values and the settings it can not override, `secret_keys` the substring match
* Not changed, documented in the README (Stable identifiers and addresses, Known limitations and gotchas): the retries of the connections that cannot come up (a TODO), the unchecked master/parent ids, `ipv6_addr_gen_mode` and `ipv6_privacy` of 0 (a deliberate choice for servers); the `mac_address` of a bond or bridge is used only for the DUID; open decisions: the default `$ipv6_dhcp_duid_default => 'auto'` makes a bond, bridge or vlan without `mac_address` fail unless `ipv6_method` is `ignore`/`disabled` or an `ipv6_dhcp_duid` is set (kept on purpose: the DUID is what binds an address to a host, see the README)

## 1.0.0-rc1 -> 1.1.0
* Behaviour changes to check when upgrading:
    - the values are validated more strictly: the `Networkmanager::DNS_IPV4`, `DNS_IPV6` and `IPV4_CIDR` types used unanchored patterns and accepted almost any string, they now validate the whole value; `$ipv6_dhcp_duid` of `connection` (any string before) is validated by the new `Networkmanager::DHCP_DUID` type as it is in `bond` and `bridge`; a malformed value which used to slip through now fails to compile
    - the values of the keyfiles are formatted by `networkmanager::ini_value` according to the GLib key file rules: arrays are written as `a;b;` (they were rendered as `[a, b]`), the backslash, new line, tab, carriage return and edge spaces are escaped so that a value can not break the file
    - only the `method` is written to the `ipv4` section when it is `disabled` and to the `ipv6` section when it is `ignore` or `disabled`, the other settings have no effect there (the idea of the pull request jednoprsak/PuppetNetworkManagerModule#24 by kbucheli), the sections are prepared by `networkmanager::prepare_ipv4_config` and `networkmanager::prepare_ipv6_config`
    - `networkmanager::ifc::bridge` ignored `$ipv4_dns`, it is written now
    - the `hash2stuff` dependency was removed (jednoprsak/PuppetNetworkManagerModule#30), the keyfiles and `NetworkManager.conf` are rendered by the bundled `templates/ini.epp`
    - the unused `NMMod::*` types and the unused `networkmanager::get_ipv6_duid` function were removed
* New features:
    - `$networkmanager::ipv6_dhcp_duid_default` (`'auto'` by default) is used for the connections that do not set their own `$ipv6_dhcp_duid`, so a connection with the `$mac_address` does not need `$ipv6_dhcp_duid => 'auto'` any more (it failed to compile before); the value `'unset'` (for the class and for a connection) does not write the DUID so NetworkManager uses its own default; a connection with the `auto` DUID and without the `$mac_address` still fails, with a message that points to the ways out (jednoprsak/PuppetNetworkManagerModule#29); the DUID is resolved by `networkmanager::resolve_ipv6_duid`
    - an ethernet `networkmanager::ifc::connection` without `$interface_name` and `$mac_address` uses its title as the interface name (it failed to compile before), a title which can not be an interface name fails with a clear message (jednoprsak/PuppetNetworkManagerModule#31)
    - `$ipv4_address` and `$ipv6_address` accept more addresses as an array or as a string separated by a semicolon, they are written as `address1`, `address2`, ... (a single address is still written as `address`), verified with NetworkManager from 1.10.12 to 1.54 (jednoprsak/PuppetNetworkManagerModule#33)
    - `$ipv4_dns` and `$ipv6_dns` accept also an array of up to 5 addresses (validated by the `stdlib` IP address types), the semicolon separated string is still accepted and may contain compressed IPv6 addresses
    - [OpenVox](https://voxpupuli.org/openvox/) 7 and 8 are supported and tested in the CI (`OPENVOX_GEM_VERSION` selects it in the `Gemfile`)
    - supported: `puppet` `>= 4.9.2 < 9.0.0` and `puppetlabs/stdlib` `>= 5.2.0 < 11.0.0` (verified against the individual releases); operating systems AlmaLinux, Amazon Linux, Arch Linux, CentOS, Debian, Fedora, Gentoo, Manjaro, Oracle Linux, RedHat, Rocky and Ubuntu (jednoprsak/PuppetNetworkManagerModule#30)
    - `REFERENCE.md` describes the classes, defined types, functions, data types and the fact
* Fixes:
    - `networkmanager::ifc::connection`, `::bond`, `::bridge` and `::vlan` build their keyfile through the new `networkmanager::compact_keyfile` function, the generated files are unchanged
    - `vlan_parent` is a managed connection `$id` or a plain UUID (NetworkManager does not accept any prefix like `UUID=`), documented and tested; the parent interface name is deliberately not supported (jednoprsak/PuppetNetworkManagerModule#34)
    - the example in the README used a connection id shorter than the 3 characters required, an invalid DUID and had missing commas, it compiles now (jednoprsak/PuppetNetworkManagerModule#32)
    - the error for an unsupported OS family names the family instead of the garbled message
    - `networkmanager::ipv6_disable_version` does not fail before NetworkManager is installed (the fact is missing then)
    - typos in the documentation, the comments and the messages
* Maintenance:
    - the spec tests were rewritten to run against every operating system release listed in `metadata.json`, a GitHub Actions workflow runs the metadata, syntax and lint checks and the specs on Puppet 6, 7 and 8 and OpenVox 7 and 8
    - the parameters of the classes and defined types are documented in the `@param` format and the lint has no warnings
    - the PDK leftovers (Travis, GitLab and AppVeyor configs, `.rubocop.yml`, `.sync.yml`, `pdk.yaml`, `.yardopts`, `.pdkignore`, the dev container and VS Code settings, the `pdk-*` and `template-*` keys of `metadata.json`) were removed and the `Rakefile` was reduced to the tasks used by the tests

## any -> 1.0.0-rc1
* Breaking changes:
    - the `$ifc_name` parameter was renamed to `$interface_name`
    - connection `$id` is by default limited to 3 to 15 characters, because it is used as the default value of `$interface_name`, which is limited to a maximum of 15 characters by the kernel. You can change this behaviour by adjusting `$networkmanager::max_length_of_connection_id`, then you need to supply the `$interface_name` where applicable if you use `$id` longer than 15 characters
    - The parameters got their limits adjusted so they expect the right types (eg. `$vlan_id` was accepted as a string before, now it must be an integer from 1 to 4094 inclusive). The changes are almost everywhere, so check your code (it will just fail to compile)

* New features:
    - added the untested support for Debian
